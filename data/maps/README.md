# Region maps: how the pins work

## What this is
Every `data/maps/{region}_pins.json` maps PokeAPI location-area slugs
(e.g. `viridian-forest-area`) to an approximate position on that region's
map. **Every pin position is a best guess** based on general knowledge of
each region's in-game layout, not real coordinate data — PokeAPI doesn't
provide map coordinates for locations, only names.

There are two different pipelines depending on the region, because Kanto's
map art works differently from every other region's.

## Which region is a location in? (`location_area_regions.json`)
`app/main.py` needs to know a location's region to pick both the map to show
and the pins file to search. **A game's generation does not tell you
this** — the remakes and multi-region games break that assumption badly:

| games | generation | actually set in |
|---|---|---|
| FireRed / LeafGreen | 3 | Kanto |
| Gold / Silver / Crystal | 2 | Johto **and** Kanto |
| HeartGold / SoulSilver | 4 | Johto **and** Kanto |
| Omega Ruby / Alpha Sapphire | 6 | Hoenn |

`data/maps/location_area_regions.json` is a flat
`{location_area_slug: region}` index built from the bulk cache by
`prep/build_area_regions.py`, and it's authoritative. Verified: no
slug is claimed by more than one region, so the mapping is unambiguous.

Because one generation can span two regions, `get_encounters()` buckets
encounters by **(generation, region)** rather than generation alone —
HeartGold gives you a "Johto · Gen IV" tab and a "Kanto · Gen IV" tab,
each with its own map, instead of one tab showing Sinnoh's map with no
pins on it.

## Coordinate system (both pipelines)
- 0-100 on both axes, origin (0,0) at the **top-left**.
- x increases going **right/east**, y increases going **down/south**.
- These are percentages of the map's width/height, not pixels, so they
  work at any render size, regardless of that region's native SVG viewBox.

## Kanto: legacy, procedurally-generated landmass
Kanto is the special case. Its map SHAPE is generated FROM the pins
themselves (an ellipse fit around the pin coordinates, pixel-noise
coastline) — see `prep/build_kanto_map.py`. There's no real reference art to
align against; the coastline is just a rough approximation sized to
comfortably contain wherever the pins land.

- `data/maps/kanto_pins.json` — the source of truth. Edit this to move pins.
- `app/static/maps/kanto.svg` — the compact map shown in the app. Generated.
- `app/static/maps/kanto_calibration.svg` — a large version with a 10-unit grid
  and every pin labeled, for reading off corrected coordinates. Generated.
- `prep/build_kanto_map.py` — regenerates both SVGs from `kanto_pins.json`.
  Run `python3 prep/build_kanto_map.py` after editing the pins file.

To adjust a Kanto pin: open `app/static/maps/kanto_calibration.svg`, read off
the x/y off the gridlines, edit `data/maps/kanto_pins.json`, and re-run
`prep/build_kanto_map.py`.

## Every other region: real map art, generalized pin builder
Johto, Hoenn, Sinnoh, Unova, Kalos, Alola, and Galar all have real,
fixed map art in `app/static/maps/{region}.svg`, built once from reference
images in `images for claude/` via `prep/pixelate_map.py`. That art is
never regenerated by the pin workflow — pins get placed to align with
whatever's already drawn there.

- `data/maps/location_pins/{region}.json` — **hand-authored input**, one
  entry per named place (city/route/dungeon), NOT per location-area:
  `{"blackthorn-city": {"x": 82, "y": 12, "label": "Blackthorn City"}}`.
  This is the actual content work.
- `prep/build_region_pins.py` — mechanically expands that into
  `data/maps/{region}_pins.json` (what `app/main.py` actually reads), using
  the offline PokeAPI bulk cache (`data/raw/region`, `data/raw/location`)
  to find every location-area slug under each authored location and give
  it the same x/y as its parent (verified: every location-area slug is a
  direct extension of its parent location's slug across all 7 regions —
  e.g. `galar-route-2-main`/`-lake`/`-lakeside` all share one point, same
  as how Kanto's own `mt-moon-1f`/`b1f`/`b2f` already work). Also
  generates `app/static/maps/{region}_calibration.svg` — the region's real
  map art with a grid + labeled dots overlaid, for visual QA.
  Run `python3 prep/build_region_pins.py <region>|all`.
- `prep/check_pin_completeness.py` — standalone sweep across all 7
  regions' generated `*_pins.json`, printing any location-area slug the
  bulk cache knows about that has no pin yet. Run with no args.

`label` is a build-time/calibration-only field — `app/main.py`'s
`get_encounters()` only ever sends `{x, y}` to the frontend, so label
quality only affects how readable the calibration SVG is, not runtime
behavior.

A rare exception: some locations' areas are meant to scatter across the
map instead of sharing one point — e.g. Hoenn's `mirage-spot-*` DexNav
locations, whose area slugs are literally named by relative position
(`north-of-fortree`, `west-of-rustboro`). For those, `AREA_PIN_OVERRIDES`
in `prep/build_region_pins.py` sets a per-area coordinate that takes
precedence over the inherited location coordinate.

To adjust a non-Kanto pin: open `app/static/maps/{region}_calibration.svg`,
edit the location's x/y in `data/maps/location_pins/{region}.json`,
re-run the build script for that region.

## Known gaps (not authoring omissions)
- **Paldea**: the PokeAPI bulk dataset has zero location-area encounter
  data for all 84 Paldea locations — `"areas": []` everywhere. Genuinely
  nothing to pin; Paldea pokemon show the plain unpinned location list
  (or nothing) regardless. `data/maps/paldea_pins.json` stays `{}`.
- **Kalos**: partially affected the same way. 60 of its 106 locations —
  including `kalos-route-1` itself — have no location-area data upstream.
  The other 46 are fully pinned.
- **Kanto's Sevii Islands** (FireRed/LeafGreen postgame — Mt Ember, Lost
  Cave, Tanoby Ruins, Treasure Beach, ...): 54 areas, unpinned because
  the archipelago simply isn't drawn on `app/static/maps/kanto.svg`. Pinning
  them would put dots in empty ocean. Fixing this properly means
  redrawing Kanto from a reference image via the generalized pipeline
  above, instead of the procedural blob it uses today.
- **Orre** (Colosseum / XD): no map art for that region at all, so those
  locations list without dots. `AREA_TO_REGION` at least stops them
  being drawn on Hoenn's map.

## Scope
All 7 real-art regions are fully pinned (0 missing per
`prep/check_pin_completeness.py`). Kanto is at 104/158 areas — all of
the mainland, with only the Sevii Islands outstanding for the reason
above. Across every cached encounter, 94.7% of location rows now resolve
a dot, up from 66.8% before the region-routing fix.
